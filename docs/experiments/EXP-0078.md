# EXP-0078: fast-decode block mode 27 (`cdec`)

Status: complete. Decision: **KEEP** (see the end of this file). The hypothesis
section was written and committed before any measurement.

## Motivation

On the research corpus Bite decodes 3–10x slower than the references (Bite
0.59–0.86 s; zstd -19 0.11 s, Brotli 11 0.14 s, xz -9e 0.23 s on the reference
machine). The cost comes from the adaptive arithmetic and context-model
decoders used by modes 10–25. No Bite point is on the size/speed Pareto
frontier.

## Hypothesis

A new block mode 27 can keep most of Bite's parsing advantage while removing
adaptive coding from the decode loop. It reuses the wide-history
(16 MiB window) `WideMatchIndex` match finder with a cost-based parser, and
codes the result with static per-block tANS tables:

* zstd-style sequences (literal length, match length, offset) with bucketed
  codes plus raw extra bits, and a four-entry recent-distance cache whose
  codes 0–3 replace the offset;
* one backward bitstream with three interleaved tANS states for the
  sequence codes;
* literals either as four interleaved order-0 tANS streams (bulk decoded, then
  16-byte wild copies), or as a static context model: up to 64 clustered tANS
  tables selected by a key over the 1–6 preceding decoded bytes (generic rank
  map; no file-type dispatch), chosen by exact encoded size per block;
* a forward optimal parse priced from the previous encoding's actual tables
  (greedy seed plus three iterated passes, exact-selected by size);
* a decoder loop with no model updates, bounded copies with 32 bytes of
  slack, multi-byte (16/8-byte) match copies, and full bounds validation.

Predictions, pre-registered:

1. Research-corpus aggregate below zstd -19 (3,384,473 bytes on the
   reference machine), ideally below xz -9e (3,360,808).
2. Process-harness decode time within 1.5x of zstd -19, measured as a
   same-machine ratio in this cloud environment.
3. `cmax`, `cfast`, `cbwt` and every historical mode stay byte-identical,
   because id 37 returns before any historical path executes.

The decision is KEEP if (1) holds against zstd -19 and (2) holds. Otherwise
it is REJECT, with the numbers recorded.

Assigned identifiers: block mode 27, `compress_linked_blocked` entropy_parse
id 37, CLI preset `cdec`.

## Implementation

`src/bite_fastdec.h` (included by `src/bite.c`) holds the encoder and decoder.
The stream format is described in [docs/format.md](../format.md#mode-27-fast-decode-static-tans-exp-0078).
`cdec` calls `compress_linked_blocked(..., 37)`, which returns before any
historical path runs. It builds one `WideMatchIndex` (16 MiB window, 2,048-deep
longest-match chain), then for each block (up to 16 MiB):

1. It encodes two seeds: all literals, and a greedy parse over the index.
   The cheaper one supplies the first price model.
2. It runs three forward optimal-parse passes. A pass prices literals per
   position (from the chosen literal model), LL/ML/OF codes from the previous
   encoding's normalized tANS tables, and extra bits exactly. Candidates are the
   four repeat distances plus a 64-deep chain walk that keeps, for each length,
   the nearest distance, plus the index's deep longest match. Segments end at
   4,096 positions or where no match crosses; matches of 512+ bytes are taken
   immediately.
3. Every encoding exact-selects the literal mode (raw, order-0 x4, or context
   orders 1–6 with clustered tables). The smallest full block wins, and a raw
   block is stored if mode 27 does not beat it.

Two design points came from the first screen, described below rather than
hidden. The first full run (3,430,232 bytes) parsed E.coli into 453K short
matches, because 4-byte matches priced like 2-bit order-0 literals. Adding the
literal-only seed and ranking only the bytes present (instead of forcing byte 0
into the alphabet) let the order-6 context model win E.coli: 1,216,482 → 1,108,891
bytes. Decoding those 4.5M context literals cost ~6 ns each. A shared tANS state
across tables, a rolling bit-packed key, and rank-coded symbols took E.coli from
~60 ms to ~35 ms. Neither change uses file names, extensions, corpus position or
file-type dispatch: every choice is an exact size comparison over generic
candidates.

## Results: decode time (same-machine ratios only)

All timings come from one Firecracker cloud VM (4 vCPUs) with
`bin/bite` built by `make` (cc 13.3, -O3). They are **not** reference-machine
timings and are valid only as ratios against zstd -19, measured in the same
session. This VM was visibly noisy: the same zstd E.coli decode ranged
13–140 ms at different times, and CPU steal was recorded. So there are three
measurements, all with a fresh process per decode and the output written to a
file:

| Measurement | cdec | zstd -19 | xz -9e | Brotli 11 | cdec / zstd |
|---|---:|---:|---:|---:|---:|
| A. `benchmark.py --stage screen --repeats 3` (median of 3) | 0.4060 s | 0.1036 s | 0.2220 s | 0.2603 s | 3.92 |
| B. `benchmark.py --repeats 1 --decode-repeats 11` (median of 11) | 0.1287 s | 0.0878 s | 0.2111 s | 0.1239 s | **1.47** |
| C. decode-only, codecs interleaved per file, median of 15 | 0.0826 s | 0.0745 s | 0.2071 s | 0.0834 s | **1.11** |

Run A follows the harness's default protocol. Each `cdec` decode runs right
after that repeat's `cdec` encode of the same file, which takes ~100 s for E.coli.
A controlled check (60 s busy loop, then decodes) slowed zstd and `cdec` decodes
alike, but only `cdec` has long encodes before its decodes, and only the large
files moved (E.coli 0.198 s in A vs 0.041 s in B). B adds an opt-in
`--decode-repeats` option to the same process harness; the default of 1 keeps
historical behaviour. C (`results/exp-0078-decode-interleaved/`) removes
encode-to-decode adjacency and time drift between codecs.

Process start-up (1.3–2.5 ms per decode) dominates those, and Bite reads and writes whole
buffers. The genuine weakness is E.coli: 4.54M of its 4.64M bytes are
context-coded literals on a serial key → table → state dependency chain
(~6 ns each), 2.7–4.1x slower than zstd in every run, while Brotli 11 is 1.7x.
`bible.txt` is 0.8x in C but 2.3x in B, which tracks the noise. Encoding is
slow: 328 s for the corpus in B, against 7 s for zstd -19 and 29 s for Brotli 11.
Peak encode RSS is 138 MB and peak decode RSS 7.4 MB (GNU time).

## Verification

* All 16 research files round-trip in every timing run, and all 26 dev
  files round-trip under `cdec`. `cbwt` and `cmax` (new build) round-trip
  all 42 dev + research files.
* Byte identity with a main build (`1b288da`): `cmax`, `cfast` and `cbwt` on
  10 files each (research `paper1`, `progc`, `obj1`, `geo`, `trans`; dev
  `alice29.txt`, `fields.c`, `sum`, two small files), and 14 historical modes
  (`c`, `cl`, `cb`, `clb`, `cbh`, `clbh`, `cblink`, `clblinkh`, `clblinks`,
  `clblinksopt2`, `clblinksopt2dfsbw`, the `...tdlmmdcr` endpoint, `...a4`
  and `...a4f`) on 3 files each. All 72 are identical, and each output also
  decodes with the new decoder (`results/exp-0078-verification/`).
* ASan+UBSan (gcc, `-fno-sanitize-recover=undefined`): `cdec` round trips of
  all 42 dev and research files are clean.
* `scripts/test_fastdec.py` under ASan+UBSan: five synthetic streams (text,
  DNA, binary records, runs, tiny) cover order-0, context and sequence paths.
  It checks 1,297 truncations and short payloads with consistent block
  headers, all rejected with status 1. It also applies 1,500 random byte and
  bit corruptions plus oversized varint counts: none crashes or trips a
  sanitizer. 992 corruptions decode to different bytes. Mode 27 has no
  checksum, and a near-uniform DNA tANS table is a fixed 2-bit code, so such
  flips are undetectable, as with zstd without `--check`.
* Build: clang 18 compiles `src/bite.c` with no warnings under
  `-Wall -Wextra -Wpedantic`. GCC 13 reports only the five warnings that main
  already has (lines in historical code), none in `bite_fastdec.h`.

## Decision: KEEP

Prediction 1 holds with margin: 3,316,040 bytes is below zstd -19 and xz -9e
on the research corpus, in this environment and against the reference-machine
figures. Prediction 3 holds: no historical output changed. Prediction 2 holds
in the two runs that control for VM noise (1.47x and 1.11x) but not in the
default 3-repeat harness run (3.92x). That run is confounded by
encode-adjacent slowdowns in this VM, so it does not settle the question
either way. Because size is authoritative and the speed criterion is met
under controlled measurement, `cdec` is kept as a candidate fast-decode
point. Its decode ratio must be re-validated on the reference machine, alone,
before any Pareto claim.

Follow-ups that the data supports:

1. E.coli context-literal decoding is the main speed gap. Decoding two
   symbols per lookup for small alphabets, or a lower context order chosen by
   a decode-cost penalty, should be measured.
2. `cdec` encoding (~330 s) needs a cheaper chain or fewer passes before it
   is a practical preset.
3. On dev, `kennedy.xls` and `pseudo_text.bin` lose to zstd -19. This points
   at minimum match length 4 and the lack of a delta/record transform.
