# EXP-0085: faster context-mixed BWT second stage (mode 29, `cbwt3`)

Status: done, KEEP. The hypothesis section below was written and committed
(cb9ba5e) before any mode-29 code and before any `cbwt3` measurement on either
corpus. It is unchanged.

## Motivation

EXP-0077's `cbwt2` (mode 26) is 2,953,704 bytes on the 16-file research corpus
(13,787,888 bytes). It is the only Bite point near the size/speed frontier that
EXP-0080 measured (bsc 2,980,242 bytes in about 1 s). But it is slow. On this
M1 (same build, `bin/bite-bench`, 1 repeat, research corpus):

| | encode s | decode s |
|---|---:|---:|
| `cbwt` (mode 25) | 3.68 | 1.42 |
| `cbwt2` (mode 26) | 14.52 | 11.78 |
| of which BWT sort (prefix doubling, this branch) | 3.37 | — |
| of which inverse BWT | — | 0.05 |
| BWT sort with EXP-0083 SA-IS (main) | 1.90 | — |

So about 11.2 s of encode time and 11.7 s of decode time is the mode-26 model.
That is about 100 ns per coded bit (110 M binary decisions). Every bit runs 17
inputs through four 17-weight mixers plus a final mixer, two APMs, and 14
counter updates that each divide by the hit count.

Measured on the BWT output itself: 54.2% of research bytes (58.1% of dev bytes,
`random.bin` excluded) equal the previous byte, and another 15.5% (4.6% on dev)
equal the previous distinct byte. Mode 26 still spends 8 mixed decisions on each
of those bytes.

## Hypothesis

A new block mode 29 (`cbwt3`) keeps the BWT, the 32-bit binary arithmetic coder,
the framing and the raw fallback of mode 26. It changes only the model:

1. **Run flag first.** Every byte starts with one binary decision "equals the
   previous byte". It is predicted from a few small contexts (run-length
   bucket, previous byte, recent flag history). Only on a miss are the 8
   literal bits coded. For the last literal bit, the value that would rebuild
   the previous byte is impossible, so that bit is not coded. About half the
   bytes then cost 1 decision instead of 8.
2. **Ablation.** Each mode-26 input (order 0/1/2, run-bucket, distinct-byte
   contexts, fast counters, bit histories, symbol-rank inputs) and each mixer
   selector is removed one at a time. The loss is recorded per model, and only
   inputs that pay for their cost are kept.
3. **Cheaper arithmetic.** Reciprocal lookup instead of division in counter
   updates; one shared hash per byte for several context tables; fewer or
   smaller mixers (one or two weight sets in place of four plus a final layer);
   one APM instead of two if that is nearly free.

Prediction (fixed before measuring):

- Size: `cbwt3` is at most 1% larger than `cbwt2` on the research corpus, that
  is ≤ 2,983,000 bytes. A secondary aim is to stay below bsc's strongest
  2,980,242 bytes.
- Speed, as same-machine ratios of `bin/bite-bench` medians on the research
  corpus:
  - decode at least 3x faster than `cbwt2`;
  - model-stage encode at least 3x faster.
  - End-to-end encode is capped by the shared BWT sort. With this branch's
    prefix doubling (3.37 s), 3x end-to-end encode would need the model under
    1.5 s, and I expect only about 2.5x. With EXP-0083's SA-IS sort applied to
    both codecs (as they will be once merged), I expect at least 3x.

Decision rule: KEEP if every dev and research file round-trips, the research
total is ≤ 2,983,000 bytes, and decode and encode are both at least 3x faster
than `cbwt2`. Encode is judged on the authoritative comparison, where both
codecs use the same BWT sort (this branch merged with main's SA-IS, measured in
a scratch build). The ratio on this branch alone is also reported. Otherwise
REJECT, or report the result as a size/speed trade-off without a mode change.

Tuning discipline: model structure and constants are chosen on the development
corpus (`corpus/dev`, `random.bin` excluded as in the harness default). Research
totals are checked once settings are frozen and are not tuned per file. The
hold-out corpora are not touched. Mode 26 stays byte-identical.

## What was built

Block mode 29, preset `cbwt3` (CLI, `bin/bite-bench`, `bite-bwt3` in both
benchmark scripts). The transform, the 32-bit binary arithmetic coder, the
framing and the raw fallback are mode 26's. Modes 25 and 26 are byte-identical.
No `compress_linked_blocked` id was used (39 stays free), and `cmax`/`cfast`
are unchanged.

Payload: u32 primary row, a 32-byte bitmap of literal values, one 4-bit code
length per literal value, then the arithmetic code (4-byte flush, as in mode 26).

Model, per byte:

1. **Run flag.** One decision, "equals the previous byte". Inputs: each
   context's slot 0 plus its bit-history counter (9 inputs). One mixer, with a
   weight set selected by (run bucket, last 4 flags), then one APM on the same
   key, averaged with the mixer output.
2. **Literal**, only on a miss. Each block gets a canonical prefix code from
   its literal frequencies: Huffman, with frequencies halved until no code is
   longer than 15. Literals are coded as branch decisions down that tree, not
   as 8 fixed bits. Internal node ids are 1..255, so they index the same
   256-slot context windows that `c0` indexed in mode 26. A branch whose child
   is the previous byte's leaf is forced and costs no decision. This
   generalises "skip the last bit"; with all code lengths 8 it reproduces the
   plain 8-bit model exactly (checked: 2,070,919 dev bytes in both forms).
   Inputs per decision (12): four contexts × (slot, bit-history counter), fast
   order-0 and order-1 counters, the symbol-rank input for the previous
   distinct byte, and a bias. Two mixers (selected by tree node and by run
   bucket) feed a 2-weight final mixer per node. Then two APMs (node; previous
   byte × node), averaged.
3. **Contexts:** order 0, (c1, run bucket), (c1, d2), (c1, d2, d3). Each hashed
   context owns a 256-slot window per byte, so one hash serves both the flag
   (slot 0) and every literal node. A slot is one 32-bit word: 18-bit
   probability, 6-bit hit count (adaptive rate 1/(n+1.5), limit 60) and the
   last up to 7 bits seen there. Bit-history counters are fixed-rate (>>5),
   fast counters >>2.
4. **Arithmetic:** reciprocal table instead of division, a squash lookup
   table, int32 mixers that the compiler vectorises (weights clamped to ±8.0),
   and encoder and decoder specialised at compile time. No floating point.

Model memory is about 19 MB for blocks of 128 KiB and larger: 3 × 4 MiB
context windows, a 2 MiB fast table and a 4.3 MB APM. Mode 26 needs about
33 MB.

## Profile of mode 26 (before)

On this M1, the mode-26 model took about 11.2 s of the 14.5 s research encode;
the other 3.37 s is the shared prefix-doubling sort. That is about 100 ns per
binary decision. Mode 26 is instruction-bound, not memory-bound: about 9,200
instructions per dev byte at IPC 4.2. Every bit computes 17 inputs, four
17-weight mixers, a final mixer, two APMs and 14 counter updates, each with a
division. In the first run-flag prototype, shrinking the hash tables 64x saved
only about 10% of the time, so the work had to come from fewer instructions,
not from better cache use.

## Ablation

Sizes are dev-corpus totals (`random.bin` excluded), model on cached BWT
output plus framing. The cost column is encode instructions retired
(`/usr/bin/time -l`), which is deterministic, unlike wall time on this shared
machine.

Three of the four first-layer mixers are each worth under 0.01%. Removing the

### Steps to mode 29

| step | dev bytes | encode instructions |
|---|---:|---:|
| mode 26 | 2,071,992 | 77.8 G |
| run flag first, mode-26 inputs, two mixers | 2,072,392 | — |
| packed slots, 6-bit counts, int32 mixer | 2,070,919 | 22.8 G |
| + second flag "equals d2" (rejected) | 2,081,271 | 22.2 G |
| + prefix-code literals | 2,072,665 | 20.1 G |
| fixed-rate bit-history counters (>>6) | 2,073,221 | 18.8 G |
| drop order-1 and order-2 contexts | 2,076,902 | 15.4 G |
| retune rates (fast >>2, history >>5, mixer lr) | **2,073,097** | **15.3 G** |

The second flag lost 1.9% on the dev text files: its own small model predicted
d2 worse than the literal model's rank input did. The prefix code costs about
1,500 dev bytes of headers (32 bytes plus half a byte per literal value, per
block), but cuts work by 12% on dev and by 24% on the dev text files. The dev
`gradient.rgb` and `readings.f64` have almost no runs (2%) and broad literal
alphabets, so dev understates the gain.

## Verification

- `cbwt3`, `cbwt2` and `cmax` round-trip through the CLI (`bite PRESET`, then
  `bite d`) on every dev and research file: 42 files x 3 presets = 126 round
  trips, 0 failures.
- Byte identity with an `origin/exp-0077-bwt-entropy` build: `cbwt`, `cbwt2`,
  `cmax`, `cfast` and `clb` on alice29.txt, kennedy.xls, small_0000.bin
  (empty), small_0017.bin, paper1, obj1 and geo (35 streams, all identical).
  Research and dev totals for `cbwt` and `cbwt2` match EXP-0077 exactly.
- `python3 scripts/test_bwt.py`: 1,075 forced round trips through modes 25, 26
  and 29 (exhaustive small binary strings, all-equal, period-7, ramp and random
  inputs at power-of-two boundaries, and a Fibonacci-skewed input that needs
  length limiting). Direct tests cover length limiting, the one-literal sibling
  and rejection of an incomplete code. `cbwt3` CLI round trips cover empty,
  1 byte, all-zero (empty literal code), all-equal, periodic, random and
  4-letter inputs, and sizes 16 MiB − 1, 16 MiB and 16 MiB + 1, decoded with
  `d`, `dwork` and `dslow`. The 87 new mode-29 rejection cases are every
  truncation, trailing data, an out-of-range primary, extra bytes inside the
  block, a block ending inside the coder flush, a payload shorter than its
  fixed fields, a present literal with code length 0, lengths that do not
  form a complete code, and a nonzero padding nibble. Plus 100 random bit
  flips. Totals: 217 rejection cases and 300 mutations, all passing.
- `python3 scripts/test_bwt.py --sanitize` (clang ASan + UBSan, macOS):
  the same 1,075 round trips, 217 rejection cases and 300 mutations pass with
  no sanitizer report. The harness now disables leak detection on macOS, as
  EXP-0083 does on main (same hunk), because Apple's ASan aborts on
  `detect_leaks=1`.
- Build: Apple clang `-Wall -Wextra -Wpedantic` is warning-free for `bin/bite`,
  `bin/bite-bench` and `tests/test_bwt.c`, at `-O3`, `-O2` and the sanitizer
  flags.

## Against the m1-2 frontier bar (added after the results)

This section was added after the results above, when same-machine m1-2
reference timings arrived (`results/m1-2-reference-levels-research/` on main,
process harness, single-threaded). It is not part of the pre-registered rule.
The bar set for a frontier point: be smaller than zpaq -m4 in under about 8 s,
or be smaller than bsc's strongest setting in well under 8 s, for example at
most about 2.95 MB in 2–4 s each way.

| codec (m1-2) | research bytes | encode s | decode s |
|---|---:|---:|---:|
| zpaq -m4 | 2,928,430 | 8.02 | 9.15 |
| `cbwt2` | 2,953,704 | 10.80 | 9.27 |
| **`cbwt3` (estimate, see below)** | **2,974,452** | **~4.0 (~2.8 with SA-IS)** | **~2.0** |
| bsc `-e2srca` | 2,980,242 | 0.77 | 0.60 |
| bsc `-e2` | 2,981,300 | 0.62 | 0.60 |
| PPMd o16 | 3,005,110 | 2.02 | 2.16 |
| zpaq -m3 | 3,049,251 | 3.21 | 4.87 |

The `cbwt3` times are estimates, not m1-2 measurements: m1-2's `cbwt2` times
scaled by this machine's ratios: encode 10.80 s / 2.70 on this branch; with
SA-IS, 10.80 s × 3.30 / 12.59 (SA-IS `cbwt3` over this branch's `cbwt2`, which
is what m1-2 ran); decode 9.27 s / 4.62. Sizes
are exact; per-file sizes are in the research table above, so the comparison can
be redone once `cbwt3` is timed on m1-2.

Judgement: `cbwt3` meets the second arm only narrowly. It is the only measured
point that is smaller than bsc's strongest setting and faster than zpaq -m4, so
none of these references dominates it. But it is just 5,790 bytes (0.19%)
smaller than bsc, at about 4–5x bsc's encode time and about 3x its decode time.
It misses the example target of about 2.95 MB by about 24 KB. It is a weak
frontier point, not a clear one. Getting there would take about 0.8% more on
research. The dev ablation suggests order-1 and order-2 contexts are worth only
about 0.15% at +22% work, so that needs new modelling (for example, the text
losses on book1 and obj1), not adding back what was removed.

## Decision

KEEP mode 29 / `cbwt3`. On the research corpus it is 2,974,452 bytes: +0.70%
against `cbwt2`, within the pre-registered 1% (≤ 2,983,000), and below bsc's
strongest 2,980,242. With both codecs on the same SA-IS sort, it is 3.36x
faster to encode and 4.72x faster to decode than `cbwt2`. Every file
round-trips. The prediction held for decode (≥ 3x: 4.6–4.7x) and for
model-stage encode (≥ 3x: about 6.5x). On this branch alone, end-to-end encode
is 2.70x, close to the 2.5x I expected; the prefix-doubling sort is now 72% of
`cbwt3` encode time.

Against the later m1-2 frontier bar (previous section), `cbwt3` is only a
marginal frontier point: 0.19% smaller than bsc at an estimated 3–4 s, not
about 2.95 MB.

Follow-ups: merging with main (EXP-0083 SA-IS) is what turns the encode
win into 3.4x, so mode 29 should land together with or after EXP-0083. Order-1
and order-2 contexts are the cheapest way to buy back size (−0.15% dev for +22%
work), but that is far short of the ~0.8% needed for ~2.95 MB. Reference-machine timing should confirm the ratios before `cbwt3` is
considered for `cmax`.
