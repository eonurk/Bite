# EXP-0080: size-oriented reference compressors

Measurement only: no codec change, nothing in `src/`. The research plan says the
practical codecs (zstd, xz, Brotli) are not sufficient size targets. This
experiment measures BWT, PPM and context-mixing references on Bite's own corpora
to show how much size headroom is left.

**Result.** All three of these families beat Bite `cmax` on the research corpus.
zpaq `-m5` is 13.6% smaller (440,844 bytes), bsc `-e2` is 8.2% smaller, and 7-Zip
PPMd is 6.2% smaller. Only bzip2 is larger. Brotli 11, the current practical
target, is 1.1% larger than `cmax`. Bite's remaining gap to a strong reference
is therefore an order of magnitude larger than its lead over Brotli. cmix, run
only on four small Calgary files, is 32% smaller than `cmax` and 23% smaller than
zpaq on those files.

## Setup

- **Harness.** `scripts/benchmark.py`, one repeat (`--stage screen --repeats 1`),
  with exact round-trip comparison on every file. The new codecs run only when
  named with `--codecs`, so default audits and external-row caches are unchanged.
- **Machine.** Linux cloud container (Ubuntu 24.04, 4 vCPU Intel Xeon, 15 GiB).
  **All timings in this document are cloud timings.** They are not comparable
  with the local macOS timings in earlier experiments. Size is authoritative.
- **Peak memory.** From GNU time `%M` (KiB × 1024). This is maximum RSS, so it is
  comparable across codecs here but is not the macOS `time -l` figure.
- **Bite cross-check.** `bite-max-bwt` (`cmax`, built from `main` at `1b288da`)
  was rerun in the same harness. It reproduces the recorded 3,247,227 bytes on
  the research corpus exactly, and every per-file size matches
  `results/exp-0075-bwt-research-inprocess`.

### Corpus provenance

This container's network policy blocked `corpus.canterbury.ac.nz` (403), so
`make research-corpus` and `make corpus` could not download the pinned archives.
Instead, the corpus files were copied from the `pfalcon/canterbury-corpus` GitHub
mirror. Each file was accepted only if its SHA-256 matched the per-file hash that
this repo already records for the same path:
`results/exp-0067-strong-references-research/metadata.json` for research and
`results/exp-0068-small-alphabet-order4-dev/metadata.json` for Canterbury.
All 16 research files and all 11 Canterbury files matched. The bytes are
therefore identical to those the fetch scripts produce.

The one exception is the generated `scientific_data/readings.f64`, which
`scripts/generate_corpus.py` writes with `math.sin`. Linux glibc and macOS libm
differ in the last bits, so the Linux file has a different SHA-256 (`7253107a…`
instead of `2550e6ca…`). Every dev comparison below was therefore measured on
the same Linux bytes, Bite included. Do not compare dev aggregates against
earlier macOS dev results.

No hold-out corpus was touched.

### Codecs

| Harness name | Command | Family |
|---|---|---|
| `bzip2-9` | `bzip2 -9` | BWT + MTF + Huffman |
| `bsc` | `bsc e IN OUT` (defaults: `-b25 -m0 -cf -e1`, LZP on) | BWT + QLFC |
| `bsc-max` | `bsc e IN OUT -e2srca` | BWT + adaptive QLFC, segmentation, reordering, context autodetect |
| `ppmd-7z-mx9` | `7z a -t7z -m0=PPMd -mx=9` (order 32, 192 MB model) | PPMd var.H |
| `zpaq-m5` | `zpaq a ARC f -m5` | context mixing (ZPAQ method 5) |
| `cmix` | `cmix -c IN OUT`, no dictionary | context mixing + LSTM |

7-Zip and zpaq write archives rather than bare streams. `scripts/archive_codec.sh`
stores each input under the fixed name `f`, so container overhead does not depend
on the corpus path. The overhead is still counted in the size: about 70–110 bytes
per file for 7z and about 1,000 bytes per file for zpaq. On the research corpus
that is about 16 KB of zpaq's total, or 0.6%. It matters only for the dev
small-file fixtures.

**bsc strongest setting.** `bsc` documents `-e2` as "best compression". Block
size does not matter here because every file fits in the default 25 MB block.
The optional preprocessing flags were swept on the research corpus. Because that
sweep chose the setting on the research files themselves, `bsc-max` is a
corpus-selected ceiling for bsc, not a blind setting:

| bsc options | Research bytes |
|---|---:|
| default (`-e1`) | 3,002,482 |
| `-e2` | 2,981,300 |
| `-e2p` (no LZP) | 2,982,724 |
| `-e2s` | 2,980,294 |
| `-e2ca` | 2,981,248 |
| `-e2cp` | 2,991,792 |
| `-e2m5` / `-e2m6` (sort transform) | 3,093,570 / 3,046,084 |
| `-e2srca` (chosen) | **2,980,242** |

`-e2m8` failed on this build. On research, everything after `-e2` moves bsc by
only about 1 KB. On dev, the same flags matter much more: `-s`/`-r` take
`gradient.rgb` from 1,159,770 to 6,424 bytes, which explains why dev `bsc` and
`bsc-max` are so far apart.

## Gaps these references reveal

1. **Natural-language text is the main gap, and it is in modelling, not
   parsing.** On book1, book2, bible.txt, world192.txt and the papers, bsc beats
   `cmax` by 10–15% and zpaq by 15–23%. Together, bible.txt and world192.txt
   alone account for 266,833 bytes of zpaq's 440,844-byte lead. bsc uses no
   context mixing, only a BWT plus an adaptive QLFC coder, and it still wins
   each of the four large text files (book1, book2, bible.txt, world192.txt) by
   12.8–15.0%. So Bite's `cmax` text path, whether it picks the LZ path or the
   EXP-0075 BWT + MTF + zero-run path, misses most of what a better post-BWT
   coder already recovers. The next ceiling, zpaq's order-n + word context
   mixing, is roughly another 6% beyond bsc-max in aggregate.
2. **A tuned BWT backend is the cheapest step.** Bite `cmax` (3,247,227) sits
   between bzip2 -9 (3,364,810) and bsc (3,002,482). Replacing MTF + zero-run
   with a QLFC-style adaptive coder, or modelling the BWT output directly with
   context-mixed binary decisions, could plausibly recover most of the 245 KB
   to bsc at BWT-class speed. bsc decodes the whole corpus in 1.0 s (cloud),
   against Bite's 2.6 s.
3. **Binary and structured data: obj2, geo, kennedy.xls, ptt5.** zpaq is
   20–22% smaller on obj2 and geo, and 35% (ptt5) to 77% (kennedy.xls) smaller
   on dev. bsc-max gains little or nothing on obj2, kennedy.xls and ptt5, so this
   gap belongs to CM-style structure modelling: record and stride contexts, sparse contexts, and
   column-wise mixing. LZ and BWT do not close it. On geo, even Brotli beats
   `cmax`.
4. **E.coli is already near the BWT/CM references.** zpaq is only 1.2% ahead
   and bsc-max is behind Bite. The EXP-0068 order-4 small-alphabet model is
   competitive. A DNA-specific CM such as cmix's would move this file further,
   but it is not where the general gap lies.
5. **Where Bite wins:** tiny files (container overhead), `gradient.rgb` (189
   bytes, against 5–6 KB for the references), `records.bin`, and against zpaq
   only, short Canterbury source and markup (fields.c, grammar.lsp, xargs.1),
   where zpaq's models cannot warm up. bsc-max beats Bite on those three short
   files too and is within 0.2% of Bite on the dev aggregate.
6. **Headroom versus cost.** zpaq -m5 reaches 1.63 bpb at about 0.4 MB/s in
   both directions and 148 MiB RSS (cloud). Bite `cmax` encodes at about
   0.03 MB/s (cloud) and decodes at 5.3 MB/s. A symmetric CM decoder would give
   up Bite's decode-speed advantage. Of the three references, the BWT/QLFC route
   (bsc) is the one compatible with Bite's fast-decode goal.

## Reproduce

```sh
sudo apt-get install bzip2 7zip zpaq time   # Ubuntu 24.04 versions listed above
./scripts/fetch_reference_codecs.sh         # bsc v3.3.12 and cmix v21, hash-pinned
make research-corpus corpus bin/bite
python3 scripts/benchmark.py --stage screen --repeats 1 --corpus-dir corpus/research \
  --aggregate-exclude --codecs bzip2-9 bsc bsc-max ppmd-7z-mx9 zpaq-m5 bite-max-bwt \
  --label exp-0080-references-research
python3 scripts/benchmark.py --stage screen --repeats 1 --corpus-dir corpus/dev \
  --codecs bzip2-9 bsc bsc-max ppmd-7z-mx9 zpaq-m5 bite-max-bwt \
  --label exp-0080-references-dev
```
