# EXP-0081: pre-registered holdout-2026 corpus

Status: **locked**, 2026-10-17. This experiment assembles and locks data
only. It changes no codec, and no Bite mode or other compressor has been run
on any hold-out file.

| Lock field | Value |
|---|---|
| Corpus root | `corpus/holdout-2026/` (ignored by Git through `/corpus/`) |
| Fetch script | `scripts/fetch_holdout_corpus.sh` |
| Lock digest | `6a6061d06fd8037f81a13309b4783f61018bd335751e2909cb14d45082297c2a` |
| Files | 37 in six categories, 144,681,868 bytes |
| Downloads | 36, each pinned by SHA-256 |
| Fetch record | `results/exp-0081-holdout-fetch/` (`dry-run.log`, `fetch.log`, `MANIFEST.json`) |

The lock digest is the SHA-256 of the lines `"<sha256>  <bytes>  <path>\n"`
for every corpus file, sorted by path. The script refuses to install a corpus
whose download hashes, file count, total size or lock digest differ from the
pinned values. `MANIFEST.json` lists every file's path, size, SHA-256,
category, source URL, download name and derivation.

```sh
scripts/fetch_holdout_corpus.sh --dry-run   # verify everything, install nothing
scripts/fetch_holdout_corpus.sh             # verify, then install corpus/holdout-2026
```

## Why a new hold-out

Canterbury, Calgary and the Canterbury Large Corpus have been used for
tuning, and Silesia has already been observed (`results/holdout-silesia-*`).
The generated hold-out has duplicate fixtures. Several improvement
experiments now run in parallel, so the overfitting risk is growing. Item 2 of
`RESEARCH_PLAN.md` asks for an independent corpus of real data whose hashes
and settings are frozen before evaluation. holdout-2026 is that corpus. Any
claim that Bite beats a default compressor must rest on it, evaluated under
the protocol below.

## How files were selected

Files were chosen by **category, provenance, stability of the URL, licence
and size only**. Selection was not informed by how Bite, or any other
compressor, would do:

- No Bite mode and no compressor ran on any candidate or chosen file.
  Compressibility was neither measured nor estimated. Release archives were
  only *decompressed* to derive their files.
- Sizes came from HTTP `Content-Length`, archive listings or the derived
  file. The only content inspection was `file(1)` type detection, used to
  confirm that each file has its stated format and is not a Git LFS pointer.
- No candidate was rejected after any look at content. One substitution was
  made for size alone: the Django 5.1.2 sdist unpacks to 61 MB, which would
  have pushed the corpus above its size budget, so the pytest 8.3.3 sdist
  replaced it.

URLs are immutable where possible. Repository files use
`raw.githubusercontent.com` at a full commit SHA, and binaries and tarballs
are maintainer-uploaded release assets or registry artifacts. Auto-generated
GitHub source archives are avoided because their bytes have changed in the
past. Where the publisher provides a checksum, the pinned hash was checked
against it, and all of them matched:

| Download | Publisher checksum checked |
|---|---|
| ripgrep 14.1.1 (both archives) | release `.sha256` files |
| jq 1.7.1 (three binaries, source tarball) | release `sha256sum.txt` |
| fzf 0.55.0 linux_amd64 | release `fzf_0.55.0_checksums.txt` |
| pytest 8.3.3 sdist | PyPI JSON `digests.sha256` |
| typescript 5.6.3 tgz | npm `dist.integrity` (sha512) |
| guava 33.3.1-jre jar | Maven Central `.sha1` (no `.sha256` is published) |

Every other file is pinned by the SHA-256 recorded at first fetch. Each of
those files is addressed by an immutable commit-SHA URL.

### Host availability

The build session's network policy only allowed GitHub, PyPI, npm and Maven
Central, so the choice of sources was limited to those hosts. The suggested
enwik9 slice (mattmahoney.net) was blocked, as were Project Gutenberg, Zenodo
(full Loghub), Wikimedia, sqlite.org, kernel.org and the Canterbury corpus
site. This restriction is about reachability, not content, and it does not
affect independence. It does mean the natural-language material is older than
ideal (see Limitations).

### Overlap avoidance

- No file comes from the Canterbury, Calgary, Large, or Silesia corpora, or
  from `scripts/generate_corpus.py`.
- Some Gutenberg books in the NLTK bundle duplicate development or research
  texts, so they are excluded by name before any content was examined:
  `bible-kjv` (Large `bible.txt`), `carroll-alice` (Canterbury `alice29.txt`),
  `milton-paradise` (Canterbury `plrabn12.txt`) and all three `shakespeare-*`
  plays (same author and edition family as Canterbury `asyoulik.txt`).
- Silesia overlaps are avoided by kind: there is no Samba source (Silesia
  `samba`), no Mozilla or OpenOffice binaries, no Dickens or Webster text, and
  no SAO star catalogue.
- The 37 hold-out SHA-256 values were compared with all 57 distinct corpus
  file hashes recorded in `results/*/metadata.json` (dev, generated, research
  and Silesia). There is no exact duplicate. The evaluation repeats this check
  (protocol step 3).

## Limitations (stated before any result)

- The natural-language text is older than "modern": Gutenberg books, Europarl
  sessions from 2000, and the UDHR. The modern Wikipedia slice (enwik9) was
  unreachable. UDHR is parallel text, so cross-language structure is present.
- Category sizes are unequal. The structured category is dominated by one
  17.8 MB CSV, and the source category by the curl tar. Totals weight
  categories by bytes, so per-category aggregates are always reported
  alongside them.
- The JPEG files are small, so the compressed category is mostly archive bytes.
- At 145 MB, a three-repeat `cmax` process run takes hours at current encode
  speed. This is accepted, and it is not a reason to subsample.

## Locked evaluation protocol

The protocol may be amended only **before the first hold-out evaluation run**,
by a commit to this file that gives the reason. After the first run it cannot
be changed.

### Until evaluation

1. Nobody runs Bite or any compressor on `corpus/holdout-2026`. Nobody opens,
   samples or profiles its files, or uses them in screens, validation runs,
   tests or parameter searches.
2. The corpus is never used to choose between candidates. Development uses
   `corpus/dev` and `corpus/research` only.

### What is evaluated

- **Bite presets**: `cmax` and `cfast` (`bin/bite cmax|cfast INPUT OUTPUT`,
  decoded with `bin/bite d`). A later preset may be evaluated only after it is
  *frozen*: its name, format identity and parameters are committed and it has
  passed the development and research acceptance checks. It must be named in
  the evaluation experiment's document before that run starts.
- **Bite commit**: every preset under evaluation is frozen at one commit, and
  the evaluation document records that commit and the `bin/bite` SHA-256
  before running.
- **Reference codecs and settings**: these are fixed. Each runs as a
  single-threaded CLI to stdout, with default windows and no dictionaries,
  `--long` or large-window flags:

  | Name | Compress | Decompress |
  |---|---|---|
  | gzip-6 (default) | `gzip -6 -c` | `gzip -d -c` |
  | gzip-9 | `gzip -9 -c` | `gzip -d -c` |
  | bzip2-9 | `bzip2 -9 -c` | `bzip2 -d -c` |
  | xz-6 (default) | `xz -6 -c` | `xz -d -c` |
  | xz-9e | `xz -9e -c` | `xz -d -c` |
  | zstd-3 (default) | `zstd -q -3 -c` | `zstd -q -d -c` |
  | zstd-19 | `zstd -q -19 -c` | `zstd -q -d -c` |
  | zstd-22 | `zstd -q --ultra -22 -c` | `zstd -q -d -c` |
  | brotli-11 (default) | `brotli -q 11 -c` | `brotli -d -c` |

  Tool versions are whatever is installed on the reference machine at run
  time, and the harness records them. Adding another reference, such as cmix
  or ZPAQ from item 1 of the plan, needs a protocol amendment before the first
  run.

### Metrics

- **Per file**: the complete compressed size in bytes, including all headers
  and framing, and bits per byte (`8 × compressed / original`). The exact
  round trip is checked on every file.
- **Aggregate**: total compressed bytes and aggregate bits per byte
  (`8 × Σcompressed / Σoriginal`) over **all 37 files**. Nothing is excluded
  from the aggregate (pass `--aggregate-exclude` with no values). Per-category
  aggregates are reported for each of the six categories. For each Bite preset
  and each reference, the report also counts per-file wins, ties and losses.
- **Timing and memory**: encode and decode time and peak RSS come only from
  the process harness (`scripts/benchmark.py`), with three repeats and the
  median reported, on the **reference machine** only. That machine is the
  Apple M1 MacBook Pro (Darwin arm64) used for the existing process-harness
  results. Runs on any other machine report sizes only. In-process timings
  are not reported for the hold-out, and wall-clock and CPU times are never
  compared as if they were interchangeable.

### Procedure

1. Write the evaluation experiment document with the Bite commit, the binary
   hash, the presets and this protocol's commit, then commit it.
2. Run `scripts/fetch_holdout_corpus.sh`. It must report lock
   `6a6061d0…297c2a` with 37 files and 144,681,868 bytes.
3. Check that no hold-out SHA-256 equals any file hash in `corpus/dev` or
   `corpus/research`. If one does, drop that file and say so in the report.
4. Run the process harness once on the reference machine:
   `python3 scripts/benchmark.py --stage audit --repeats 3 --corpus-dir
   corpus/holdout-2026 --aggregate-exclude --codecs <the presets and the
   references above> --label exp-NNNN-holdout-2026`, without
   `--baseline-cache`, so every reference row is measured fresh. The only
   allowed harness change beforehand is adding `Codec` rows for `cfast` and
   `bzip2-9` that use exactly the command lines above.
5. Commit the complete output directory unedited, together with the report.

### Reporting rule

- **Results are reported once.** A completed run is never repeated to get a
  better number. A run that aborts for an infrastructure reason (crash,
  machine loss) may be repeated at the same commit, and the abort is
  recorded. A round-trip failure counts as a result, not an abort.
- **No tuning afterwards.** Nothing learned from hold-out results may change
  a preset and then be re-evaluated on holdout-2026 as if it were independent
  evidence. A change motivated by the results is a new preset. Its hold-out
  numbers carry the caveat that earlier hold-out results were known. A fresh
  claim needs a new pre-registered corpus (holdout-2027).
- **Claims**: "Bite `<preset>` beats `<reference>` on holdout-2026" requires a
  strictly smaller total compressed size over all 37 files. Every such claim
  also reports the per-category aggregates and the per-file losses. A subset
  of files or categories never stands in for the full corpus.
