# EXP-0077: context-mixed second stage for the BWT path (mode 26, `cbwt2`)

Status: done, KEEP. The hypothesis section was written and committed before the
mode-26 implementation and before any `cbwt2` research-corpus measurement.

## Hypothesis

Mode 25 (`cbwt`) codes the cyclic BWT with move-to-front ranks, zero-run
lengths and one adaptive order-1 frequency model over the byte tokens. That
stage throws away most of the structure of the BWT output. Run ends are coded
with no knowledge of the run length so far, the second-most-recent distinct
symbol is not modelled, and a single frequency table adapts slowly to the
locally changing statistics of the sorted contexts.

Proposed mode 26 keeps the transform identical and replaces the second stage
with direct binary context mixing over the BWT output bytes. Each output byte
is coded as 8 binary decisions with a 32-bit binary arithmetic coder. Every
decision mixes a fixed number of predictions:

- adaptive-rate counters for order-0, order-1 (previous byte), order-2,
  (previous byte, run-length bucket), (previous byte, previous *distinct* byte)
  and (previous byte, two previous distinct bytes) contexts;
- fast fixed-rate ("two-rate") counters for the order-0 and order-1 contexts;
- an indirect bit-history model per context (last up to 7 bits seen in that
  slot, mapped to a probability by an adaptive table keyed by run bucket);
- shared symbol-rank models predicting "next byte equals the previous byte" and
  "equals the previous distinct byte", keyed by run bucket and bit position;
- a two-layer logistic mixer (four first-layer weight sets selected by partial
  byte, previous byte, run bucket x partial byte and run bucket) followed by
  two interpolated SSE stages (partial byte; previous byte x partial byte).

Work per input byte is a fixed number of table lookups and updates, so cost is
linear in the block size.

Prediction (fixed before measuring): `cbwt2` will be below xz -9e
(3,360,808 bytes) and below Brotli 11 (3,283,714 bytes) on the 16-file research
corpus, and below `cbwt` (3,373,378 bytes) on every research file of at least
20 KB. Encode and decode will be several times slower than `cbwt`, because
every byte costs 8 mixed binary decisions instead of about one frequency-coded
token. KEEP if the research total beats xz -9e and every file round-trips;
REJECT otherwise.

Tuning discipline: model structure and constants were chosen on the
development corpus (Canterbury plus the text-like generated files, excluding
`random.bin`, `gradient.rgb`, `readings.f64` and the small files). Research
totals were only checked, never optimized per file. No hold-out corpus was
touched.

## Implementation

- `src/bite_bwt.h`: `bwt2_encode`/`bwt2_decode` (block mode 26). The payload
  is a u32 primary row followed by a 32-bit binary arithmetic code. Probabilities
  are 12-bit and the coder flushes exactly 4 bytes, so the decoder must consume
  every payload byte. Truncated payloads and trailing payload bytes are rejected.
  The inverse transform moved into a shared `bwt_inverse` helper. Mode-25
  coding is unchanged.
- Model: the inputs listed in the hypothesis (17 per bit), with four first-layer
  mixers and a final mixer selected by partial byte. Then two APMs, averaged.
  Hashed context tables have `2^min(20, max(12, ceil(log2(8 * block))))` slots,
  so memory scales with block size. The peak is about 33 MB of model state
  for blocks of 128 KiB and larger, on top of the BWT itself. The model uses no floating
  point; squash is a fixed interpolation table.
- `cbwt2` CLI preset and `bin/bite-bench` mode, with framing and the raw
  fallback identical to `cbwt`. The new codec entries are `bite-bwt2` in both
  benchmark scripts.
- No `compress_linked_blocked` entropy_parse id was used (36 stays free), and
  `cmax`/`cfast` are unchanged.

## Corpus provenance

`corpus.canterbury.ac.nz` was blocked (HTTP 403) by this cloud environment's
network policy, so the pinned-archive fetch scripts could not run. The research
and Canterbury files came from the `github.com/pfalcon/canterbury-corpus`
mirror. Every file matched that mirror's SHA1SUM lists, the 16 research
files total exactly 13,787,888 bytes, and a main-branch build reproduces the
published `cbwt` sizes file by file (3,373,378 total, as in the EXP-0075
baseline). The research corpus was used only for measurement. No hold-out
corpus was used.

## Timing (cloud-relative only)

Measured in this cloud container, same process harness, same files, 3
repeats on the research corpus. These numbers are not comparable with the
reference-machine measurements and only the ratio is reported:

- encode time `cbwt2` / `cbwt`: 3.96x
- decode time `cbwt2` / `cbwt`: 9.90x

The decoder now does the same per-bit model work as the encoder. Mode 25
decoding was dominated by a cheap order-1 frequency decode.

## Development notes (dev-corpus tuning, ideal code length)

These steps were measured on the dev text-like subset; research totals were
only checked:

| step | research total (ideal) |
|---|---:|
| order 0/1/2 + run counters, one mixer (lr too high) | 3,192,305 |
| lower mixer learning rate | ~3,058,000 |
| + (c1, d2, d3) context, fast counters on order 0/1 | 3,011,539 |
| + symbol-rank (c1, d2) inputs | 3,007,236 |
| + two-layer mixer (4 selectors) | 2,966,757 |
| + indirect bit-history inputs, lr retune | ~2,952,500 |

Hashed tables with 2^20 instead of 2^22 slots cost 667 bytes in total, so
production uses 2^20. Separate weight sets per selector mattered most: one
mixer with 4,096 sets learned too slowly. Ideas not tried, for later
experiments: 16-bit final probabilities (most bits in long runs sit at the
12-bit floor), bit-history state machines in place of 7-bit raw histories,
and a learning-rate schedule (a quick decaying-rate test was neutral).

## Verification

- `cbwt2`, `cbwt` and `cmax` round-trip on every dev and research file
  (42 files x 3 presets = 126 round trips, decoded with `d`, 0 failures).
- Byte identity with a main-branch build: `cbwt` on every dev and research
  file; `cmax`, `cfast`, `clb` and
  `clblinksopt2dfsbwasp2b16x2tdlmmdcra4cm3` on alice29.txt, kennedy.xls,
  small_0000.bin (empty), small_0017.bin, paper1, obj1 and geo.
- `python3 scripts/test_bwt.py` covers 1,074 forced mode-25 and mode-26 round
  trips (exhaustive small binary strings plus all-equal, period-7, ramp and
  random inputs at power-of-two boundaries). It also runs `cbwt2` CLI round
  trips (empty, 1 byte, all-equal, periodic, random, 4-letter, and sizes
  16 MiB minus one, 16 MiB and 16 MiB plus one). Malformed cases cover every truncation, trailing
  data, an out-of-range primary, extra bytes inside the block, a short block
  and an undersized payload. Together with the mode-25 cases, that is 130
  rejection cases plus 200 random bit flips (100 per mode). It passes plain and with `--sanitize` (ASan+UBSan; run with gcc
  because this image lacks clang's sanitizer runtime).
- Build: clang `-Wall -Wextra -Wpedantic` is warning-free. gcc 13 reports the
  same 5 warnings as main (all in pre-existing LZ code); none come from mode
  26. On Linux, `bin/bite-bench` needs `-D_POSIX_C_SOURCE=200809L` for
  `CLOCK_MONOTONIC`, as on main.

## Decision

KEEP. `cbwt2` reaches 2,953,704 bytes on the research corpus: -12.44% against
`cbwt`, below xz -9e (3,360,808) and 10.05% below Brotli 11 (3,283,714). Every
file round-trips, and all historical presets checked stay byte-identical. The
cost is speed: in this environment cbwt2 takes ~4x as long as cbwt to encode
and ~10x as long to decode, still linear per symbol. Reference-machine timing
should be validated separately before mode 26 is wired into `cmax`
(entropy_parse id 36 remains available for that).
